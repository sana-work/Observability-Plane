How ai-observability-sdk captures a request

The SDK is a small Python library each of the 8 AI services installs. One line at startup + one decorator per hot path, and every request produces structured events on Kafka, a trace in Tempo, and JSON logs — all three joined by one correlation_id — while also contributing to Prometheus metrics (aggregate counters, no per-request identity) for alerting. Press Play below and watch real requests travel through it — across different services.

The three signals — event | log | metric

The envelope's telemetry_type field names three kinds of telemetry. Each answers a different question and travels a different road — the SDK produces all three, joined by the correlation_id.

📨 event → Kafka

“What happened, in business terms?”

One structured record per occurrence: LLM call completed — 1440 tokens, $0.0027, prompt v3, finish_reason stop. Validated against the 50-type contract, enriched downstream, stored in ES / Postgres / S3. This is what the simulator above shows.

📝 log → stdout → Fluent Bit → ES

“What did the code say while doing it?”

Free-text detail for humans. configure_logging() makes every line JSON and stamps correlation_id on it automatically — so logs join to events without any effort at call sites.

📈 metric → /metrics → Prometheus

“What are the aggregate numbers right now?”

Pre-aggregated counters and latency histograms per route, scraped from /metrics. Cheap, real-time, no per-request detail — this is what alerts fire on.

ℹ️ Today the SDK emits only telemetry_type: "event" onto Kafka — logs and metrics travel their own roads. The field is a reserved discriminator so a log- or metric-shaped record could ride the event pipeline later without a schema change.

🎯 The four capture points — one decorator each

Teams don't hand-write events. They decorate the function that does the work; the SDK times it, nests it, and emits the correct pair — including the failure and timeout paths everyone forgets. (For lifecycle facts with no function to wrap — a plan created, feedback submitted — services call emit_event() directly, as the Orchestration and Feedback scenarios show.)

🧠 @trace_llm

@trace_llm(model_provider="vertexai",
           model_name="gemini-1.5-pro")
async def generate(prompt):
    r = await vertex.generate(prompt)
    r.obs_payload = {
      "input_tokens": r.usage.in_t,
      "output_tokens": r.usage.out_t,
      "finish_reason": r.finish}
    return r

Captures tokens, auto-computed cost, latency, TTFT, finish reason, prompt version. prompt_text is auto-hashed — raw prompts never ride in events.

🛡 Why services trust it — the hard guarantees

Never blocks

produce() only appends to an in-memory queue; a C background thread does all network I/O. No customer request ever waits for Kafka — try the “broker down” scenario above.

Never raises

Every failure — broker outage, full queue, bad payload — becomes a log line + a counter (emitter_stats(): delivered / dropped / invalid), never an exception in your request path.

Validated at the edge

Constructing an event checks it against the frozen contract — a typo'd event type fails in unit tests. A wrong AI_OBS_SERVICE_NAME refuses to boot instead of silently emitting nothing.

Ordered per request

Kafka key = correlation_id ⇒ all events of one request land on one partition, in order — so downstream consumers replay each request's story sequentially.
